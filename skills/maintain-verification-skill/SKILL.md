# Maintain a Verification Skill

A feature map rots the moment the app changes. This skill is the upkeep loop for a skill generated by `/create-verification-skill` (or any project-local verification skill with a feature map). The unit of rigor is the feature, not every sentence: cover every feature file from source and exercise every feature live, without terminalising every bullet.

---

## Outcomes

Pick one outcome and report it explicitly:

- **clean**: Every feature received source and live coverage; nothing worth shipping. No branch, no PR.
- **changed**: One PR ships proven documentation, harness, or feature map corrections.
- **blocked**: Coverage could not finish or a proven fix could not ship safely. State the blocking cause with precision.

---

## Edit Scope

Only edit the verification skill's own directory (its `SKILL.md`, `features/`, and any harness scripts it owns). Never edit product code during an upkeep pass. A discrepancy between the map and the app is either:
- **Doc drift:** The app changed intentionally, but the map lagged behind. Fix the map.
- **Product regression:** The app broke. Report it directly to the user; never paper over a bug by weakening the verification map.

---

## Pass Steps

### 0. Locate the Target
Find the verification skill to maintain: the project-local skill whose body defines launch/drive sections and a feature map (typically `verify-*/` in `.cursor/skills/`, `skills/`, `.claude/skills/`, or `.agents/skills/`). If several candidates exist, ask the user which to audit. If none exist, stop and recommend `/create-verification-skill`.

### 1. Index Hygiene
Read the feature map `README.md` and glob its sibling files. Repair missing, extra, duplicate, or dead entries. Keep it lightweight without generating redundant inventory docs.

### 2. Source Wave
Review each feature file against current codebase logic:
- **Default (Single-Agent / Claude Code):** The lead agent audits each feature file sequentially. Protect context tokens by reading strictly the feature file and the specific route/handler files it references. Never dump broad repo trees into context.
- **Multi-Agent Mode (Opt-in / Concurrency Enabled):** If subagents are supported and configured in `setup-dzstack`, launch one read-only subagent per feature file with strict context shielding. Provide only the feature markdown and the target component paths.

Subagents or readers never drive the app and never edit files.
Return shape: `feature summary` / `source entry points` / `likely drift or none` / `one recipe`.

### 3. Reconcile
Verify every feature file has a returned summary. Merge overlapping recipes into as few runtime states as practical. Spot-check cited drift; do not re-prove clean claims. Check recent git history for new user-facing surfaces missing from the map, requiring a concrete source path before declaring one missing.

### 4. Live Pass
Required even when source code looks clean. The lead coordinator owns all driving. Follow the verification skill's own launch model: one long-lived instance driven serially for servers and UIs, or a fresh isolated session per drive for short-lived CLIs.

Exercise every feature at least once, holding three invariants throughout:
1. **Never drive an un-checked instance:** Run `doctor` before the first drive, on every fresh session, and immediately after any failed drive. When `doctor` cannot detect a hung UI state on an otherwise healthy process, reset to a clean baseline or restart the process.
2. **Evidence survives cleanup:** Confirm captured screenshots, transcripts, and logs exist at their designated locations after cleanup routines execute.
3. **No orphaned residue:** Teardown ephemeral processes and scratch state immediately after a drive finishes, whether successful or failed. For shared instances, clean fixture data while preserving the process.

If a doctor failure is caused by skill drift, fix it under edit scope and retry once before marking the pass `blocked`. If a feature cannot be reached, mark it `verified-unreachable` only with the concrete unmet prerequisite (auth, entitlement, OS capability) and the route attempted.

### 5. Triage
- **Wrong or missing user-POV description:** Doc drift: update the feature map.
- **Working behavior the harness cannot drive:** Harness gap: update the harness script, ensure it is executable, and document its invocation in the skill body.
- **App behavior is broken:** Product regression: log it clearly for the user and exclude it from the verification maintenance PR.

### 6. Ship or Stop
- **Changed:** Open one PR containing proven corrections (`gh pr create`). Re-read every modified file before opening.
- **Clean or Blocked:** No PR. Output a high-density summary reporting coverage and blockers honestly.

Store temporary run notes in `<appDataDir>/brain/<conversation-id>/scratch/` or local scratch paths; do not commit them to the repository.
